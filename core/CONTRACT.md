# Контракт core v1

Вход: `input/job.json` и `input/submissions/{submissionId}/{filename.java}`.
Работа содержит один файл, ID — UUID, имя файла — basename; исходный путь остаётся в API.
Методы: `jplag`, `structsim`. Схемы: [job](schemas/job.schema.json), [result](schemas/result.schema.json).

Выход: `output/result.json` и необязательный `output/artifacts/`.

- Каждая работа присутствует ровно один раз. `ok` включает `score`, `matches`, `stats`;
  `failed` — причину `NOT_PARSED`.
- Все `n*(n-1)/2` пар присутствуют ровно один раз; UUID упорядочены: `a < b`.
- `value` пары — 0–1 или `null` с причиной. `score` работы — максимум оценённых пар
  либо `null`; `matches` — до трёх лучших совпадений.
- `fragments` необязательны, строки нумеруются с 1, границы включены.
  Пара: `{"a":[1,3],"b":[2,4]}`; match: `{"lines":[1,3],"withLines":[2,4]}`.
- Результат воспроизводится при одинаковых входе, версии и параметрах.
  `methodVersion` и `params` отражают фактический запуск инструмента.

Коды CLI: `0` — результат записан, включая частичный; `1` — временный сбой;
`2` — неверный вход. Python API на неверный вход выбрасывает `InvalidInput`.

## Мок

Оценка: первые 32 бита SHA-256 от `mock-v1`, метода и отсортированных хешей двух исходников,
приведённые к 0–1 с округлением до четырёх знаков. ID, порядок и попытка на оценку не влияют.
Синтаксис не анализируется; даже одинаковым исходникам не гарантируется 1.0.
`details` и `stats` пусты, версия — `mock-v1`.

`fragments` вычисляются: ищутся серии совпадающих нормализованных строк между исходниками пары
(локальные идентификаторы → `V`, числа → `N`, строки → `S`), серии длиной ≥ 4 строки становятся
подозрительными участками. Так схожий код возвращает реальные диапазоны строк для подсветки
на фронте, даже пока инструмент сходства — заглушка.

Параметры `mockScenario` и `delaySeconds` задаёт воркер; [сценарии](../worker/README.md#моки).
При подключении настоящего метода сохраните вход, выход и проверки контракта.

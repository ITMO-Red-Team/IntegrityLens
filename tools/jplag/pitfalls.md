# JPlag: подводные камни

Всё перечисленное проверено на этом окружении, на **JPlag 6.3.0**.

Ещё три ловушки описаны там, где они по делу: [JRE вместо
JDK](usage.md#почему-именно-jdk) — ноль разобранных файлов без объяснения;
[кластеризация включена по
умолчанию](usage.md#ключи); [имя решения =
имя директории](usage.md#раскладка-входных-данных).

## 1. Архив обрезает пары, CSV — нет

Ключ `-n` по умолчанию 2500. Прогон 75 решений, то есть 2775 пар:

| Источник | Пар |
|---|---|
| `results.csv` | **2775** — все |
| `comparisons/` внутри `.jplag` | **2500** — обрезано |

Порог берётся уже на 72 решениях ($72 \cdot 71 / 2 = 2556$), то есть на
обычном размере учебной группы.
Разбор архива молча потерял бы часть пар, и любая метрика поехала бы вниз без
признака ошибки. **Источник оценок — только `results.csv`.**

## 2. Порог `-t` отсекает обвязку

Пара без общих кусков длиной `-t` получает **ровно 0.0**, а не маленькое
число. На пробных java-решениях пара, которая при `-t 9` даёт 0.0, при `-t 3`
даёт 0.357 — но если посмотреть, что именно совпало, оба куска окажутся
обвязкой: импорт, открытие класса, открытие `main` — и закрытие цикла, печать
ответа, закрытие метода и класса. Так начинается и заканчивается почти любое решение на Java. Алгоритма
в этих совпадениях нет.

Значит `0.0` при `-t 9` — правильный ответ, и порог нужен ровно для этого.
Механика порога на разобранном примере — в
[how-it-works.md](how-it-works.md#что-делает-порог). Что из этого следует:

- **понижать `-t` — покупать шум.** Совпадения, которые появляются на малом
  пороге, это обвязка, а не алгоритм. Если понижение порога улучшает
  результат, объяснение стоит искать не в том, что JPlag «заработал лучше»;
- **у шкалы есть точка с массой в нуле.** Пары без совпадений длиной `-t`
  получают не маленькое число, а ровно `0.0`, и таких пар много. Шкала не
  непрерывная, и при сортировке или сравнении с непрерывной мерой это
  надо учитывать отдельно;
- **общая заготовка перепрыгивает любой разумный порог.** Код, который автор
  вставляет в каждое своё решение, — такая же обвязка, только длиннее.
  Штатный ответ на это — `-bc`.

## 3. Шум в stderr

На каждом запуске печатаются четыре строки `WARNING: A restricted method in
java.lang.System has been called` от JLine. Это предупреждение Java 25 о
нативном доступе, к разбору и сравнению отношения не имеет, на код возврата не
влияет. В логах стадии отфильтровывается.

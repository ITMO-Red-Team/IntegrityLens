# JPlag: сборка, запуск, выходные данные

Проверено на **JPlag 6.3.0**. Как инструмент считает оценку — в
[how-it-works.md](how-it-works.md), найденные ловушки — в
[pitfalls.md](pitfalls.md).

## Почему в Docker

JPlag 6.3 требует Java SE 25, которой на машине может не быть, а результат
должен воспроизводиться. Образ собирается локально с прибитой версией и
проверкой контрольной суммы jar.

## Почему именно JDK

**Образ обязан содержать JDK, а не JRE.** JPlag разбирает Java настоящим
компилятором (`ToolProvider.getSystemJavaCompiler()`), а в JRE компилятора
нет.

Коварство в том, что ошибка не похожа на ошибку. На JRE JPlag запускается,
доходит до разбора и пишет:

```
Parsing Submissions   0% [                    ] 0/3
[ERROR] CLI - Not enough valid submissions! (found 0 valid submissions)
```

Ни слова о Java или о компиляторе. Файлы при этом корректные. Проверить, есть
ли компилятор внутри образа:

```bash
docker run --rm --entrypoint sh integritylens/jplag:6.3.0 \
  -c 'ls /opt/java/openjdk/bin/ | grep javac'
```

Отсюда правило: проверять не «JPlag запустился», а «JPlag выдал ожидаемые
числа на входе, ответ для которого известен заранее».

## Сборка

```bash
docker compose -f tools/docker-compose.yml build jplag
```

Что внутри [`jplag.Dockerfile`](jplag.Dockerfile):

| | |
|---|---|
| база | `eclipse-temurin:25-jdk` |
| jar | `jplag-6.3.0-jar-with-dependencies.jar`, 83.6 МБ, из релиза на GitHub |
| проверка | `ADD --checksum=sha256:5f2c21e8…` — релизные артефакты заменяемы, поэтому сумма прибита |
| `ENTRYPOINT` | `java -jar /opt/jplag/jplag.jar --mode RUN` |
| образ | `integritylens/jplag:6.3.0`, 646 МБ |

`--mode RUN` обязателен: по умолчанию режим `AUTO`, и JPlag после подсчёта
поднимает локальный веб-просмотрщик, которого в контейнере никто не увидит.

## Раскладка входных данных

JPlag берёт корневую директорию, где **каждая поддиректория — одно решение**,
а её имя становится идентификатором решения в выводе:

```
submissions/
  alice/Main.java      → решение «alice»
  bob/Main.java        → решение «bob»
  carol/Main.java      → решение «carol»
```

Отсюда следствие, на которое легко наступить: **имя решения — это имя
директории.** Переименовали директорию — поменялся идентификатор в
`results.csv`. Если вывод нужно соединять с внешней разметкой, имена
директорий должны совпадать с идентификаторами в ней.

Файлы, которые JPlag не смог разобрать, попадают в `failedSubmissions` и в
сравнении не участвуют.

## Запуск

```bash
IN=/абсолютный/путь/к/submissions
OUT=$(mktemp -d)

docker run --rm \
  --mount "type=bind,source=$IN,target=/in,readonly" \
  --mount "type=bind,source=$OUT,target=/out" \
  integritylens/jplag:6.3.0 \
  /in -r /out/report --csv-export --cluster-skip --overwrite

cat "$OUT/report/results.csv"
```

Монтирования задаются через `--mount type=bind`, а не `-v`: в `-v` путь
Windows с двоеточием после буквы диска разбирается неоднозначно. Источник
монтирования обязан быть абсолютным путём.

## Ключи

| Ключ | Зачем |
|---|---|
| `-r <файл>` | куда писать отчёт; расширение `.jplag` добавляется само |
| `--csv-export` | выгрузить пары в `results.csv` — единственный полный источник оценок, см. [ловушку 1](pitfalls.md#1-архив-обрезает-пары-csv--нет) |
| `--cluster-skip` | не считать кластеризацию: она включена по умолчанию, спектральная, и тратит время |
| `--overwrite` | затирать прошлый отчёт вместо отказа |
| `-t <n>` | минимальная длина общего куска в метках, по умолчанию 9 |
| `-bc <dir>` | общая заготовка: её метки исключаются из сравнения |
| `--normalize` | нормализация меток, поддержана для Java и C++ |
| `--match-merging` | склейка соседних кусков против попыток запутать код |
| `-m <0..1>` | порог сохранения пары; по умолчанию `0.0`, и пары с нулевой оценкой **сохраняются** — проверено |
| `-n <k>` | сколько пар положить в архив отчёта, по умолчанию 2500; на `results.csv` не влияет |
| `--log-level=DEBUG` | когда надо понять, почему файл не разобрался |

## Что получается на выходе

Один запуск оставляет **два** артефакта:

```
out/
  report.jplag                      ← zip-архив отчёта, для просмотрщика
  report/
    results.csv                     ← плоская таблица пар
    results-anonymous.csv           ← то же с обезличенными именами
    results-anonymous-names.csv     ← сопоставление id ↔ имя
```

### `results.csv`

Настоящий вывод на трёх пробных решениях, где `bob` — это код `alice` с
переименованными переменными, а `carol` устроена иначе:

```csv
submissionName1,submissionName2,averageSimilarity,maxSimilarity
alice,bob,1.0,1.0
alice,carol,0.0,0.0
bob,carol,0.0,0.0
```

| Столбец | Тип | Что это |
|---|---|---|
| `submissionName1` | строка | имя первого решения = имя его директории |
| `submissionName2` | строка | имя второго решения |
| `averageSimilarity` | `0..1` | симметричная оценка |
| `maxSimilarity` | `0..1` | односторонняя оценка |

Строка на пару, каждая пара встречается один раз, порядок строк и порядок имён
внутри строки не гарантированы — соединять по неупорядоченной паре.

### `*.jplag` — архив отчёта

Обычный zip. Нужен для двух вещей: посмотреть пару глазами в просмотрщике
JPlag и забрать служебные сведения о прогоне.

| Файл | Что в нём |
|---|---|
| `runInformation.json` | версия, время сравнения, `failedSubmissions`, число пар |
| `options.json` | все эффективные настройки прогона |
| `comparisons/<a>-<b>.json` | подробности по паре: оценки, общие куски с номерами строк |
| `files/<решение>/…` | копии исходников, чтобы просмотрщик был автономен |
| `topComparisons.json`, `distribution.json`, `cluster.json`, `basecode/*.json` | для просмотрщика |

```json
{ "version": { "major": 6, "minor": 3, "patch": 0 },
  "failedSubmissions": [], "dateOfExecution": "16/10/26",
  "executionTime": 74, "totalComparisons": 3 }
```

`executionTime` — миллисекунды на сравнение пар, без разбора.

В `comparisons/*.json` у каждого общего куска есть **номера строк и столбцов в
обоих файлах** — позиции отдаёт компилятор. Это то, чего нет в выгрузке
Semgrep, и то, на чём можно показать человеку
`a.java, строки 40–75 ↔ b.java, строки 12–38`.

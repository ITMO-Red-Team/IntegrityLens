# native: шаг 3 и тайлы на Rust

`compare.py` и `tiles.py` — эталон метода, но на всех парах набора они слишком
медленные: 50 решений занимают минуту. [`native/`](../native/) считает **те же
числа бит в бит** на порядки быстрее. Метод от этого не меняется: шаг 3 и тайлы
определены эталоном, а native — только другой способ получить их значения.

| | эталон | native |
|---|---|---|
| 50 решений ConPlag, оценки и тайлы всех 1225 пар, одно ядро | 58 с | 0.13 с |
| пара по 2 690 меток, оценка | 1 263 мс | 1.8 мс |
| пара по 2 690 меток, тайлы | 4 043 мс | 0.2 мс |
| пара по 87 900 меток (файлы по 1 МиБ), оценка и тайлы | не дождаться | 350 мс |

Как получены числа и что происходит с остальными шагами — в
[`worker/bench/README.md`](../../../worker/bench/README.md).

## Сборка и запуск

Нужен только Rust: зависимостей у крейта нет, как и у ядра на Python.

```bash
cargo build --release --manifest-path tools/structsim/native/Cargo.toml
```

```python
from structsim import native

pairs = native.score_all(programs)   # как combinations(programs, 2)
pairs[0].combined, pairs[0].tiles
```

Бинарник ищется так: переменная `STRUCTSIM_NATIVE`, затем `structsim-native` в
`PATH`, затем сборка в `native/target/release`. `STRUCTSIM_NATIVE=off` — не искать,
тогда `find_binary()` вернёт `None`.

## Почему числа те же

Это не утверждение, а тест: [`tests/test_native.py`](../tests/test_native.py)
сравнивает с эталоном через `==`, без допусков, на случайных программах (с повторами,
правками, перестановками, пустыми блоками) и на настоящих деревьях из `tests/data`.
Разовая проверка на 1225 парах настоящих решений ConPlag: 0 расхождений.

Что для этого пришлось повторить в точности:

- **выбор куска в `SequenceMatcher`.** Самый длинный, среди равных самый левый в `a`,
  затем в `b`. Другой выбор даёт другую сумму кусков, поэтому заменить это настоящей
  LCS нельзя, хотя она быстрее;
- **несимметричность.** `ratio(a, b)` и `ratio(b, a)` различаются, и оба участвуют в
  `COMBINED`;
- **встроенный `sum()`.** В CPython ≥ 3.12 он суммирует float с компенсацией
  Ноймайера. Обычное сложение расходится в последних битах;
- **порядок тайлов.** Проходы от длинных к коротким, внутри прохода по `(i, j)`, кто
  раньше, тот и забирает метки.

## Откуда скорость

Часть выигрыша даёт сам язык: сравнение чисел вместо строк и массивы вместо словарей.
Но на длинных программах выигрывает не язык, а алгоритм.

| Что | Эталон | native |
|---|---|---|
| поиск самого длинного куска | по всем вхождениям одной метки, `T²·Σp²` на вызов | по кускам из 6 меток, они на порядки реже |
| индекс вхождений | заново на каждое сравнение | один раз на последовательность |
| левая граница диапазона | перебором | двоичным поиском |
| мера по функциям | `B²` сравнений, дважды | только пока верхняя граница выше найденного; одинаковые блоки один раз |
| мера по фрагментам | множества заново на каждую пару | отсортированные списки, слияние |
| тайлы | все пары позиций на каждом проходе, `T³` | только совпавшие начала, куча по длине |

`T` — длина программы в метках, `B` — блоков в ней, `p` — доля метки в программе.

**Поиск по кускам.** В `SequenceMatcher` таблица идёт по всем совпавшим позициям. На настоящих
решениях ConPlag всего 56 различных меток, `ID` занимает 29% позиций, и `Σp²` равно 0.125: на
программе в 100 000 меток это больше миллиарда клеток. Если строить таблицу по кускам из 6 меток,
клеток в 170 раз меньше, а ответ тот же: порядок обхода сохраняется, и любой кусок не короче 6
меток виден целиком. Если самый длинный кусок короче, поиск повторяется по одной метке. На
диапазонах короче 32 меток индекс не используется.

Размер куска и порог подобраны по времени всех пар, один поток, мс:

| Куски, порог | 50 решений ConPlag | 10 по 2 000 меток | 6 по 8 000 | 3 по 32 000 |
|---|---|---|---|---|
| без индекса | 184 | 106 | 316 | 1 208 |
| 12, 32 | 162 | 55 | 70 | 56 |
| 8, 32 | 134 | 47 | 64 | 56 |
| **6, 32** | **119** | **43** | **64** | **63** |
| 6, 96 | 129 | 47 | 66 | 65 |

Случайное совпадение хешей ответ не портит. Оно может только завысить длину куска, а
кусок, выбранный как лучший, сверяется по самим меткам, и при расхождении поиск
повторяется без индекса.

**Верхняя граница для меры 3.** Сумма совпавших кусков не больше пересечения мультимножеств
меток, поэтому `2·пересечение/(|x|+|y|)` не меньше настоящего `ratio`. Кандидаты идут по
убыванию этой границы, и перебор останавливается, как только она не выше найденного: нужен
только максимум, а он от этого не меняется.

Измерено на синтетических программах: один файл, один поток
(`worker/bench/results/pair_cost.csv`).

|---|---|---|---|---|
| 324 | 23 мс | 12 мс | 0.57 мс | ~0 |
| 1 343 | 318 мс | 637 мс | 1.01 мс | 0.1 мс |
| 2 690 | 1 263 мс | 4 043 мс | 1.75 мс | 0.24 мс |
| 10 979 | — | — | 9.3 мс | 2.6 мс |
| 43 638 | — | — | 64 мс | 35 мс |
| 87 927 | — | — | 210 мс | 137 мс |

В колонках native есть и запуск процесса с передачей программ: на коротких программах это
большая часть времени.

| Часть | Эталон | native, измерено | Худший случай |
|---|---|---|---|
| оценка пары | `T²` (×3.9 за удвоение) | `T^1.3…1.6` | `T³`: длинные повторы одной строки |
| тайлы пары | `T^2.7` (×6.3 за удвоение) | `T^1.9`: синтетика из пяти шаблонов функций, совпадений много | `T²` |
| подготовка программы | на каждое сравнение | `T log T` один раз | |
| весь набор | `n²` пар | `n²` пар | |

Квадрат по числу работ никуда не девается: контракт требует оценку каждой пары, и эталон
определён на паре. Но до этого предела в наборе из 50 работ не дойти: на шаг 3 там уходит
0.07 с из двух.

## Формат

Вход на stdin, выход на stdout, всё текст, разделитель — пробел или перевод строки.

```
structsim-native/1 <программ> <меток в алфавите> <min_tile> <потоков>
<T> <метка>×T <строка>×T <B> (<длина блока> <метка>×длина)×B
…
```

- метка — номер от 0, строка — номер строки исходника или 0, если позиции нет;
- `min_tile = 0` — без тайлов, `потоков = 0` — сколько доступно процессу;
- алфавит не больше 4096 меток: пять меток куска меры 2 должны поместиться в 64 бита.

На выходе строка на пару, в порядке `combinations`:

```
<a> <b> <order> <shingle> <blocks> <combined> <K> (<start_a> <start_b> <length> <a_from> <a_to> <b_from> <b_to>)×K
```

Числа печатаются кратчайшей записью, которая разбирается обратно в то же значение.
`STRUCTSIM_NATIVE_TIMINGS=1` выводит в stderr время этапов.

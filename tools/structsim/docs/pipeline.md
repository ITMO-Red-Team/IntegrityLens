# Конвейер: что откуда вызывается

Четыре шага, между ними три границы. На каждой границе лежит ровно один тип
данных — и это всё, что следующий шаг знает о предыдущем.

```
   файл с кодом           ┌─ шаг 1 ─────────────┐
   relax.cpp         ───> │ semgrep-core        │ ───>  JSON дерева
   (один файл)            │ в контейнере        │       (dict)
                          └─────────────────────┘
                                                          
                          ┌─ шаг 2 ─────────────┐         
   JSON дерева       ───> │ обход дерева,       │ ───>  Program
                          │ узел → метки        │       labels + blocks
                          └─────────────────────┘
                                                          
                          ┌─ шаг 3 ─────────────┐         
   Program × Program ───> │ три меры,           │ ───>  float 0..1
                          │ среднее в обе сторо-│       COMBINED
                          │ ны                  │
                          └─────────────────────┘
                                                          
                          ┌─ шаг 4 ─────────────┐         
   COMBINED всех пар ───> │ фон пары и разброс  │ ───>  float
   набора                 │ по набору           │       contrast-z
                          └─────────────────────┘
```

## Границы и типы

| Граница | Что передаётся | Чем задано |
|---|---|---|
| шаг 1 → шаг 2 | JSON-дерево одного файла | формат Semgrep, [step1.md](step1.md) |
| внутри шага 2 | узел → метки | таблица в [step2.md](step2.md) |
| шаг 2 → шаг 3 | `Program` | [`model.py`](../src/structsim/model.py) |
| шаг 3 → шаг 4 | `COMBINED` по всем парам набора | `Mapping[PairKey, float]` |

Главное про эти границы: **шаг 3 не знает ни про Semgrep, ни про языки**, он
видит только последовательности меток. А **шаг 4 не знает даже про программы**
— он принимает готовые числа по парам. Поэтому шаги 3 и 4 проверяются тестами
без всякого разбора кода, а падение Semgrep на одном файле не ломает расчёт по
остальным.

## Шаг 2 → шаг 3: что такое `Program`

```python
Program(
    labels=("FUNC", "P4", "IF", "ID", "IDX", "ID", "+", "ID", ...),
    blocks=(
        Block(labels=("FUNC", "P4", "IF", ...), name="relax"),
        Block(labels=("ID", "=", "CALL", ...), name=None),   # основной код
    ),
    language="cpp",
    source="relax.cpp",
)
```

- `labels` — вся последовательность в порядке обхода. По ней работают меры 1
  и 2.
- `blocks` — та же программа, порезанная на части: каждая функция верхнего
  уровня отдельно, весь остальной код — ещё одним блоком. По ним работает
  мера 3.
- `blocks` **не** обязаны склеиваться в `labels` ровно: это два взгляда на
  одну программу, а не контейнер и его части.
- `name` у блока — имя функции до очистки. На оценку не влияет, нужен только
  для вывода вида «`dijkstra` ↔ `dijkstra` — 0.88».

## Шаг 3: три меры и почему их три

Вызывается `combined(a, b)` из [`compare.py`](../src/structsim/compare.py).
Внутри — три независимые меры, каждая от 0 до 1:

| Мера | Функция | Что видит | Что её ломает |
|---|---|---|---|
| по порядку | `order_similarity(labels, labels)` | всю последовательность | перестановка кода |
| по фрагментам | `shingle_similarity(labels, labels)` | множество кусков по 5 меток | одна лишняя метка портит сразу 5 кусков |
| по функциям | `block_similarity(program, program)` | блоки | ничего из перечисленного, зато слепа внутри блока |

`COMBINED` — среднее трёх. Мера 1 немного зависит от того, какую программу
подали первой, поэтому среднее считается в обе стороны и усредняется ещё раз:

```
COMBINED(a, b) = ( mean(м1, м2, м3 | a,b) + mean(м1, м2, м3 | b,a) ) / 2
```

Проверка этого порядка: в разборе метода пара Dijkstra C++ ↔ Python даёт
0.80, 0.25 и 0.80 по трём мерам и `COMBINED` 0.62 — а в примере про
`contrast-z` та же пара фигурирует как 0.617. Среднее трёх как раз
0.6167, так что оба числа подтверждают порядок усреднения.

Если нужно увидеть, из чего сложилась оценка, вместо `combined` вызывается
`explain(a, b)` — он возвращает все три меры и итог.

## Тайлы: какие куски совпали

Отдельный вывод, **не шаг конвейера**. Отвечает на другой вопрос: не
«насколько похожи программы», а «какие именно куски у них общие».
Вызывается `tiles_of(a, b)` из [`tiles.py`](../src/structsim/tiles.py) и
возвращает список `Tile`:

```python
Tile(start_a=12, start_b=40, length=18)   # индексы в labels, не строки кода
```

**На `COMBINED` тайлы не влияют.** Это принципиально: как только покрытие
тайлами начнёт определять оценку, метод сойдётся с JPlag и потеряет своё
отличие — три меры вместо одной.

### Почему Greedy String Tiling, а не куски из difflib

Мера 1 уже находит общие куски, но `difflib` ищет их **с сохранением
порядка**: переставленные местами функции он удержать обе не может. Для
оценки это терпимо — за устойчивость к перестановкам в методе отвечают меры 2
и 3. А для вывода нет: список, в котором переставленный кусок отсутствует,
просто врёт.

GST порядка не требует и берёт куски жадно, от самого длинного. На
переставленных блоках по 8 меток тайлы покрывают все 16, а мера 1 даёт 0.5 —
это зафиксировано тестом `test_swapped_blocks_beat_difflib`.

### Порог `MIN_TILE_LENGTH`

Значение по умолчанию 10 и **не откалибровано**. Взять 9, как `-t` у JPlag,
было бы ошибкой: у нас метки мельче. У JPlag решение из 19 строк даёт около
27 меток (≈1.4 на строку), наш шаг 2 на три строки примера — 20 меток
(≈6.7 на строку). То есть 9 меток у JPlag — примерно 6 строк кода, а 9 наших
— меньше полутора.

Порог отсекает не только короткие куски: на коде, который отличается
вставками, он может обнулить список целиком. Кусок из 8 меток, разрезанный
одной вставкой, даёт две половинки по 4 — и при пороге 5 исчезает полностью.

### Сколько это стоит

Измерено на последовательностях с реалистичным алфавитом меток:

| Длина, меток | Похожие, мс | Непохожие, мс |
|---|---|---|
| 170 | 12.8 | 3.4 |
| 250 | 34.5 | 7.5 |
| 500 | 280.8 | 39.6 |
| 1000 | 1647.2 | 145.7 |

Рост кубический: удвоение длины даёт ×6–8, тогда как у `COMBINED`
квадратичный. На непохожих парах GST дешевле `COMBINED` — он быстро
убеждается, что общего нет.

Отсюда правило использования: **оценку считать по всем парам, тайлы — только
для тех пар, на которые кто-то будет смотреть.** На десятке отобранных пар
цена незаметна, на 63 тысячах пар длинных программ — десятки часов. Если
тайлы когда-нибудь понадобятся на всём объёме, лечится хешированием кусков
(Карп–Рабин, как в JPlag), что сводит к квадратичному.

## Шаг 4: что считается по набору

Вызывается `contrast_z(scores)` из
[`contrast.py`](../src/structsim/contrast.py), где `scores` — словарь
`{pair_key(a, b): COMBINED}` по **всем парам одного набора**.

```python
scores = {pair_key("alice", "bob"): 0.81, pair_key("alice", "carol"): 0.22, ...}
z = contrast_z(scores)          # {("alice", "bob"): 2.74, ...}
```

Для пары `a`, `b`:

1. `m_a` — среднее `COMBINED` программы `a` со всеми остальными, **кроме**
   `b`; так же `m_b`;
2. фон пары = `(m_a + m_b) / 2`;
3. `σ` — разброс `COMBINED` по всем парам набора;
4. `contrast-z` = (`COMBINED` − фон) / `σ`.

Ключи делает `pair_key(a, b)` — он сортирует имена, так что порядок не важен.
Набор программ выводится из ключей, отдельным списком его передавать не нужно.

Два условия, встроенные в код:

- **не меньше пяти программ**, иначе `TooSmallSet`: на меньшем наборе фон
  считать не на чем;
- при `σ = 0` все пары получают 0.0 — если все похожи одинаково, выделять
  нечего.

Пары, которых нет в `scores`, не участвуют ни в фоне, ни в `σ`. Это нужно для
случая, когда часть файлов Semgrep не разобрал.

## Входная точка

Всё вместе собирает [`analyze.py`](../src/structsim/analyze.py), поверх него
командная строка [`cli.py`](../src/structsim/cli.py):

```python
from structsim.analyze import analyze

report = analyze("решения/задача-7")
report.top(10)                      # пары, самые похожие сначала
report.tiles("a.py", "b.go")        # куски этой пары, с диапазонами строк
report.skipped                      # что не разобралось и почему
```

`analyze` считает шаги 1–4 по всем парам, а тайлы — **только по запросу**:
они растут кубически от длины программы, и для набора из тысяч пар не нужны.

## Что в конвейере слабое

- **Java и Python расходятся на том, чего в таблице метода нет.** Методы
  класса мы считаем функциями верхнего уровня, а объявление `int x = 0`
  приравниваем к присваиванию — без этого одинаковые по устройству программы
  разошлись бы на каждой строке. Но `items.length` против `len(items)` так не
  выровнять: это `DotAccess` против `CALL`, и разница остаётся. Для языков с
  разным способом делать одно и то же шкала `COMBINED` не вполне общая;
- **`MIN_TILE_LENGTH` не откалиброван** — см. выше;
- **сквозных чисел документа воспроизвести нельзя**: пара Dijkstra C++ ↔
  Python даёт 166 и 170 меток, но самих этих программ в репозитории нет.
  Проверено то, что проверяемо: точная последовательность меток для
  разобранного в документе фрагмента (сразу на C++ и на Python), формулы трёх
  мер, арифметика `contrast-z` и граничные случаи;
- **один контейнер на файл.** Сброшенный `ENTRYPOINT` в образе существует
  ровно для того, чтобы гонять цикл внутри одного контейнера, но `dump_many`
  этим пока не пользуется. На тысячах файлов это станет обязательным;
- **тайлы показывают диапазон, а не точный набор строк.** Обход дерева идёт в
  глубину, поэтому непрерывный отрезок меток не обязан быть непрерывным
  куском строк: min–max может захватить строку, которой в тайле нет.

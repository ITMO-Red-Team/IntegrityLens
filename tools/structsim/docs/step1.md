# Шаг 1: общее дерево

Файл с кодом разбирается в синтаксическое дерево, устроенное одинаково для
разных языков. Это единственная внешняя часть метода, и она запускается в
контейнере.

```bash
semgrep-core -lang cpp -json -full_token_info -dump_ast <файл>
```

Проверено на **Semgrep 1.180.0**. Версия прибита жёстко: формат выгрузки —
внутренние структуры Semgrep, они не документированы и меняются между
версиями, причём молча. Поднять версию можно только вместе с повторной
проверкой всего, что читает выгрузку.

## Почему `semgrep-core`, а не публичный `semgrep`

У публичного CLI есть свой способ выгрузить дерево — `semgrep --dump-ast
--json`. Он нам не годится: **в нём нет позиций.** Проверено на одном и том же
файле:

| | Ключей в JSON | Позиции |
|---|---|---|
| `semgrep --dump-ast --json` | 42 | нет ни одной |
| `semgrep-core -json -full_token_info -dump_ast` | 50 | есть |

Разница между наборами ключей — ровно восемь позиционных полей: `token`,
`OriginTok`, `FakeTok`, `str`, `line`, `column`, `bytepos`, `file`. **В обратную
сторону разницы нет вообще**: всё, что отдаёт публичный CLI, есть и у
`semgrep-core`.

То есть вывод `semgrep-core` — строгое надмножество, и платим за него 7%
объёма (8149 → 8752 байт на функции из пяти строк). Поэтому публичный
`--dump-ast` не используется нигде.

Позиции нужны, чтобы тайлы можно было показать строками исходника, а не
индексами меток — см. [pipeline.md](pipeline.md#тайлы-какие-куски-совпали).

## Что получается

Конструкции разных языков попадают в дерево под одними и теми же именами:

| В коде | Узел |
|---|---|
| условие | `If`, внутри `Cond` и `Block` |
| присваивание | `Assign` |
| обращение по индексу | `ArrayAccess` |
| вызов | `Call`, аргументы — `Arg` |
| оператор | `Special` → `Op`, например `{"Op": "Lt"}` |
| имя переменной или функции | `N` → `Id` |
| определение функции | `DefStmt` → `FuncDef`, параметры `Param` |

Скобки, двоеточия, точки с запятой и отступы в дерево не попадают вовсе.
Поэтому разница в синтаксисе языков исчезает уже здесь, без нормализации.

**Есть в дереве:** структура и порядок действий, вложенность, имена
переменных и функций, вид операторов, позиции в исходнике. **Нет:**
синтаксического оформления и типов в том виде, в каком они написаны.

### Позиции

Позиция висит на узле под ключом `token` и бывает двух видов:

```json
{"token": {"OriginTok": {"str": "if", "bytepos": 50, "line": 2,
                         "column": 4, "file": "/probe/relax.cpp"}}}
{"token": {"FakeTok": ["(", null]}}
```

- **`OriginTok`** — настоящий токен из файла: есть строка, столбец и смещение
  в байтах. Нумерация строк с единицы, столбцов с нуля;
- **`FakeTok`** — узел, которого в тексте не было: Semgrep достроил его сам.
  Позиции у такого узла **нет**, формат другой — список, а не объект.

На `relax.cpp` из пяти строк вышло **41 `OriginTok` и 7 `FakeTok`**. То есть
примерно у каждого седьмого узла позиции не будет, и диапазон строк для тайла
надо собирать по тем узлам, у которых она есть.

Кроме дерева в JSON много служебного — `id_info_id`, `id_flags`,
`id_resolved`, `id_type`. Из-за этого выгрузка объёмная: функция из 5 строк на
C++ даёт около **8.7 КБ** JSON. На тысячах файлов это гигабайты, которые
лучше пересчитывать, чем хранить.

## Пример: один код на двух языках

```cpp
// C++
if (dist[v] + w < dist[to]) {
    dist[to] = dist[v] + w;
}
```

```python
# Python
if dist[v] + w < dist[to]:
    dist[to] = dist[v] + w
```

Semgrep выдаёт для обоих **одно и то же дерево**. Если убрать служебные поля и
позиции, читается оно так:

```
If                              ← условие
  Cond                          ← что проверяется
    Call
      Special Op Lt             ← оператор <
      Arg
        Call
          Special Op Plus       ← оператор +
          Arg
            ArrayAccess         ← dist[v]
              N "dist"
              N "v"
          Arg
            N "w"
      Arg
        ArrayAccess             ← dist[to]
          N "dist"
          N "to"
  Block                         ← что выполняется
    ExprStmt
      Assign                    ← dist[to] = …
        ArrayAccess
          N "dist"
          N "to"
        …
```

`if` из C++ и `if` из Python дают не похожие деревья, а буквально
совпадающие — вместе с тем, что оператор стал `Call` с `Special`/`Op` в роли
вызываемого.

В настоящем JSON у каждого узла рядом лежит `token`. Начало того же `If`:

```json
[{"token": {"OriginTok": {"str": "if", "bytepos": 50, "line": 2,
                          "column": 4, "file": "/probe/relax.cpp"}}},
 {"Cond": {"Call": [{"Special": [{"Op": "Lt"},
                                 {"token": {"OriginTok": {"str": "<", "line": 2,
                                            "column": 20, ...}}}]},
                    [{"token": {"FakeTok": ["(", null]}}, ...
```

Видно сразу три вещи: `Op` отдаётся как строка `"Lt"`, позиции идут вместе с
узлом, а скобка вызова оказалась `FakeTok` — её в исходнике на этом месте нет.

## Языки

Semgrep поддерживает около 30 языков; метод рассчитан на девять. Но
«поддерживается Semgrep» и «сходится с остальными языками» — разные вещи, и
второе проверено не для всех:

| Язык | Расширения | `-lang` | Сходимость |
|---|---|---|---|
| Python | `.py` | `python` | эталон |
| C++ | `.cpp`, `.cc`, `.cxx` | `cpp` | совпадает |
| C# | `.cs` | `csharp` | совпадает |
| Go | `.go` | `go` | совпадает |
| Java | `.java` | `java` | совпадает |
| JavaScript | `.js` | `js` | совпадает |
| Kotlin | `.kt` | `kotlin` | совпадает |
| Swift | `.swift` | `swift` | совпадает |
| Rust | `.rs` | `rust` | **одна метка расходится** |

«Совпадает» значит буква в букву: один алгоритм на этих языках даёт одну и ту
же последовательность меток, `COMBINED` ровно 1.000. Это проверяется тестами
(`test_convergence.py`), а не утверждается на словах.

Про единственное оставшееся расхождение и про то, почему такие расхождения
нельзя заметить по ошибкам — в
[step2.md](step2.md#сходимость-языков-проверяется-отдельно-для-каждого).

На остальных языках метод не рассчитан. Язык задаётся ключом `-lang` явно и по
расширению не угадывается.

## Запуск

Образ собирается из [`docker/semgrep.Dockerfile`](../docker/semgrep.Dockerfile):

```bash
docker compose -f tools/docker-compose.yml build semgrep
```

У базового образа `semgrep/semgrep` точка входа — сам `semgrep`. У нашего она
**сброшена** (`ENTRYPOINT []`), чтобы в контейнере можно было запустить shell
и прогнать цикл по многим файлам за один раз: разбор идёт по одному файлу за
вызов, и контейнер на каждый файл при тысячах файлов стоил бы часы.

Плата за это — команду приходится называть явно:

```bash
docker run --rm integritylens/semgrep:1.180.0 -help                 # не сработает
docker run --rm integritylens/semgrep:1.180.0 semgrep-core -help    # так
```

Сам `semgrep-core` лежит внутри питоновского пакета, и в пути зашита версия
Python. Dockerfile не прописывает путь руками, а спрашивает его у пакета и
кладёт симлинк в `/usr/local/bin`, так что команда зовётся по имени. Если
Semgrep переложит бинарник, сборка упадёт сразу — симлинк проверяется в той же
инструкции.

Один файл:

```bash
IN=/абсолютный/путь/к/директории/с/кодом

docker run --rm \
  --mount "type=bind,source=$IN,target=/work,readonly" \
  integritylens/semgrep:1.180.0 \
  semgrep-core -lang cpp -json -full_token_info -dump_ast /work/relax.cpp
```

Пачка файлов за один контейнер — то, ради чего сброшен `ENTRYPOINT`:

```bash
OUT=$(mktemp -d)

docker run --rm \
  --mount "type=bind,source=$IN,target=/work,readonly" \
  --mount "type=bind,source=$OUT,target=/out" \
  integritylens/semgrep:1.180.0 \
  sh -c 'for f in /work/*.py; do
           semgrep-core -lang python -json -full_token_info -dump_ast "$f" \
             > "/out/$(basename "$f").json" 2>/dev/null
         done'
```

Дерево уходит в stdout как JSON. Монтирование задаётся через
`--mount type=bind`, а не `-v`: в `-v` путь Windows с двоеточием после буквы
диска разбирается неоднозначно. Источник обязан быть абсолютным путём.

| Ключ | Зачем |
|---|---|
| `-dump_ast <файл>` | выгрузить дерево |
| `-json` | выгрузка в JSON, а не текстовым дампером OCaml |
| `-full_token_info` | добавить позиции токенов; без него их нет |
| `-lang <язык>` | каким языком считать файл |
| `-help` | проверить, что бинарник на месте и отвечает |

## Что может пойти не так

**Эти флаги ещё менее публичны, чем `--dump-ast`.** `semgrep-core` — не
пользовательский интерфейс, а внутренний бинарник, и `-dump_ast` с
`-full_token_info` не описаны в документации Semgrep. Предупреждение про
смену формата между версиями относится к ним сильнее, чем к публичному CLI.

**Опираться на устройство JSON нельзя.** Вложенность и названия полей могут
поехать на любом обновлении — без ошибки, просто то, что читало выгрузку,
начнёт видеть не то. А вот **имена узлов** (`If`, `Assign`, `ArrayAccess`)
лежат в выгрузке как обычные строки, и этого хватает, чтобы убедиться, что
разбор состоялся и что два файла дали сопоставимые деревья.

**У части узлов позиции нет.** `FakeTok` — это достроенный Semgrep узел, и у
него другой формат: список `["(", null]` вместо объекта. Код, читающий
позиции, обязан различать два вида `token`, иначе упадёт на первом же вызове
функции.

**Файл может не разобраться — но это видно.** На некоторых конструкциях
Semgrep не справляется. Проверено на нашем образе: циклы C++17 со
структурными привязками

```cpp
for (auto [a, b] : pairs) { … }
```

дают код возврата **1** и внятное сообщение
`"Other syntax error": single name expected for simple var` с номером строки.
То есть провал не тихий, в отличие от поведения публичного CLI, описанного в
разборе метода. Но пропуск такого файла — нормальный исход, а не поломка
окружения, поэтому число пропусков всё равно надо считать и сообщать: иначе
метрики посчитаются на меньшей выборке, чем кажется.

Сообщения `semgrep-core` раскрашены, и в stderr приезжают ANSI-последовательности —
их приходится вычищать, прежде чем показывать человеку.

**Часть различий теряется.** Дерево грубее кода: в Python `a = b = c = x` и
`a, b, c = x` дают одно и то же дерево. Это свойство представления, а не
ошибка — если различие важно, из выгрузки его не достать.

**Проверено только под Linux**, в том числе через WSL. Поведение в других
окружениях не проверялось.

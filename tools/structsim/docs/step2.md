# Шаг 2: очистка

Дерево из шага 1 превращается в **последовательность меток** — коротких имён
того, какого вида каждое действие. Всё, что зависит от автора или языка, при
этом пропадает.

Вход: JSON-дерево одного файла ([step1.md](step1.md)).
Выход: `Program` — последовательность, её разбиение на блоки и параллельный
массив позиций.

Код: [`labels.py`](../src/structsim/labels.py), входная функция `to_program`.

## Таблица: во что превращается узел

| Что в коде | Метки | Пример |
|---|---|---|
| имя переменной или функции | `ID` | `dist`, `v`, `w` → `ID` |
| обращение по индексу | `IDX` между базой и индексом | `dist[v]` → `ID IDX ID` |
| оператор | общий для всех языков знак | `&&` и `and` → `AND`; `+` → `+` |
| составное присваивание | знак плюс `=` | `s += x` → `ID += ID` |
| число 0, 1, 2 | `N0`, `N1`, `N2` | `n - 1` → `ID - N1` |
| остальные числа | `NUM` | `100` → `NUM` |
| строка | `STR` | `"done"` → `STR` |
| логическое, пустое | `TRUE` / `FALSE`, `NULL` | `False` → `FALSE` |
| вызов функции | `CALL`, аргументы следом | `min(a, b)` → `CALL ID ID` |
| вызов самой себя | `RECCALL` | внутри `total` вызов `total(…)` |
| условие | `IF … END` | |
| ветки | `ELIF … END`, `ELSE … END` | у каждой свой `END` |
| цикл любого вида | `LOOP … END` | `for`, `while`, `do-while` |
| определение функции | `FUNC Pn … END`, `n` — число параметров | `relax(dist, v, to, w)` → `FUNC P4` |
| объявление с инициализацией | как присваивание | `int x = 0` → `; ID = N0` |
| `return`, `continue`, `break` | `RET`, `CONT`, `BRK` | |
| начало оператора | `;` | только у выражений-операторов |
| кортеж | `TUPLE` | `(s, flag)` → `TUPLE ID ID` |
| новый список или объект | `NEWLIST` | `[s, 0]` → `NEWLIST ID N0` |
| типы, импорты, директивы, комментарии | ничего | |
| заголовок `for` | ничего | `for i in range(n)` и `for x in items` неотличимы |
| параметры функции | ничего, только счёт в `Pn` | имена параметров в метки не идут |

Условие `while` сохраняется — в отличие от заголовка `for`: `while s > 100`
даёт `LOOP ID > NUM`.

## Порядок инфиксный, а не древесный

Это главное, чего нет в разборе метода, но что следует из приведённой там
последовательности. В дереве оператор стоит **перед** операндами:

```
Call
  Special Op Lt
  Arg  →  dist[v] + w
  Arg  →  dist[to]
```

А в последовательности он идёт **между** ними: `ID IDX ID + ID < ID IDX ID`.
Поэтому обход не просто рекурсивный: у бинарных операторов, обращения по
индексу и присваивания порядок задан явно — левая часть, знак, правая.

Если бы обход был обычным, вышло бы `< + ID IDX ID ID ID IDX ID` — и это не
совпало бы с разбором метода.

Унарные и прочие неполные случаи записываются знаком вперёд: распознать их
надёжно не на чем, а молча терять оператор хуже.

## Проверяемый пример

Фрагмент из разбора метода:

```cpp
void relax(int *dist, int v, int to, int w) {
    if (dist[v] + w < dist[to]) {
        dist[to] = dist[v] + w;
    }
}
```

даёт ровно:

```
FUNC P4 IF ID IDX ID + ID < ID IDX ID ; ID IDX ID = ID IDX ID + ID END END
```

Тот же код на Python даёт **ту же** последовательность. Это главная проверка
шага 2, и она есть в тестах
(`test_matches_the_documented_sequence`,
`test_cpp_and_python_give_the_same_sequence`).

Разбор по частям:

| Метки | Откуда |
|---|---|
| `FUNC P4` | `relax` с четырьмя параметрами |
| `IF` | `if` |
| `ID IDX ID + ID` | `dist[v] + w` |
| `<` | `<` |
| `ID IDX ID` | `dist[to]` |
| `;` | начало оператора |
| `ID IDX ID = ID IDX ID + ID` | `dist[to] = dist[v] + w` |
| `END END` | конец `if`, конец функции |

Типов (`int`, `int*`, `void`) в метках нет — именно поэтому C++ и Python
сходятся: у Python их в дереве не было вовсе.

## Блоки

Последовательность делится на блоки: **каждая функция верхнего уровня —
отдельный блок, весь остальной код — ещё один**. По блокам работает третья
мера шага 3, поэтому вынос куска кода в функцию не роняет оценку.

Два решения, которых в разборе метода нет:

- **методы класса считаются функциями верхнего уровня.** В Java функция не
  бывает на верхнем уровне, и без этого `class E { int solve(…) }` дал бы
  безымянный блок без `FUNC`, а `def solve(…)` в Python — именованный блок с
  `FUNC`. Одинаковые по устройству программы разошлись бы на разбиении;
- **`main` функцией не считается** (как и сказано в разборе): её тело идёт в
  блок «остальной код», как код верхнего уровня в Python.

У блока хранится имя функции до очистки. На оценку оно не влияет и нужно
только для вывода вида «`dijkstra` ↔ `dijkstra` — 0.88».

## Позиции

Рядом с `labels` лежит `positions` — массив той же длины. У метки, которую
породил настоящий токен, там `Span(line, column, text)`; у достроенной
(`P4`, `END`) — `None`.

Позиции **не участвуют в сравнении**: шаг 3 и поиск тайлов работают по
меткам-строкам. Поэтому добавление позиций не меняет ни одной оценки, а
диапазон строк для тайла получается взятием min и max по его отрезку
(`Program.span_of`).

Токен ищется не по всему поддереву, а в пределах четырёх уровней. Глубже
поиск начинает брать токен ребёнка вместо своего: `IDX` стал бы указывать на
левый операнд вместо `[`, а `=` — на левую часть вместо знака. Там, где своё
имя лежит глубже (`FUNC`), глубина задана на месте вызова.

## Сходимость языков проверяется отдельно для каждого

Таблица выше написана **один раз** против общего дерева Semgrep, а не по одной
на язык. Так и задумано: Semgrep приводит конструкции разных языков к одним
именам узлов, и шаг 2 работает уже с нормализованным деревом.

Но Semgrep нормализует **не всё**. Каждый новый язык может закодировать
знакомую конструкцию иначе, чем те языки, на которых таблица обкатана, и тогда
метки разойдутся — молча.

Сейчас на одном и том же алгоритме (сумма положительных элементов массива)
**восемь языков из девяти дают одну и ту же последовательность** и `COMBINED`
ровно 1.000: Python, C++, C#, Go, Java, JavaScript, Kotlin, Swift. Это
закреплено в `test_convergence.py`.

Так было не сразу. Каждое расхождение оказывалось **одной** конструкцией:

| Язык | Было | Из-за чего |
|---|---|---|
| Go | 0.851 | `:=` приходит как `AssignOp(Eq)`, и `Eq` трактовался как равенство: `ID == N0` вместо `ID = N0` |
| Java | — | объявление приходит как `DefStmt(name, VarDef)`, а не `ExprStmt(Assign)`; методы класса не считались функциями |
| C# | 0.788 | индекс обёрнут в `Container(["Tuple", …])`, потому что индексатор может брать несколько аргументов: `ID IDX TUPLE ID` |
| Kotlin | 0.803 | `if` и `return` — выражения, приходят как `ExprStmt(StmtExpr(…))`, и давали лишний `;` |
| Swift | 0.639 | подстрочник вообще не `ArrayAccess`, а `Call` — от вызова функции в дереве не отличается |
| Rust | 0.806 | параметр приходит как `ParamPattern`, а не `Param`: `P0` вместо `P1` |
| JavaScript | 1.000 | ничего не понадобилось |

То есть дело не в числе языков, а в числе по-разному закодированных
конструкций — оно невелико и конечно. JavaScript сошёлся без единой правки.

Отдельный случай — **Swift**: в дереве подстрочник и вызов функции совпадают
полностью, и различить их можно только по токену из исходника (`[` против
`(`). Там, где дерево различие потеряло, его приходится брать из позиций.

### Что осталось: неявный возврат в Rust

У Rust значение возвращается последним выражением функции, без `return`, и это
даёт `; ID` вместо `RET ID` — одна метка из двадцати шести, `COMBINED` 0.894.

**Это не лечится таблицей.** В дереве хвостовое выражение Rust и вызов без
результата в конце функции Python — один и тот же `ExprStmt`; различает их
только семантика языка, которой в дереве нет. Выправить можно лишь правилом,
знающим про язык, а такого правила в шаге 2 пока нет ни одного — и это
свойство стоит сохранять, пока цена расхождения одна метка.

### Два вида расхождений, и только один лечится

- **разная кодировка одного и того же** — это **баг таблицы**. Go подаёт `:=`
  как `AssignOp(Eq)`, Java объявление как `VarDef`, C# индекс через
  контейнер. Все три — одно и то же действие, записанное деревом по-разному,
  и выравнивать его обязано шаг 2;
- **разные конструкции** — предел метода. `items.length` в Java это
  `DotAccess`, а `len(items)` в Python — `CALL`; программы правда делают это
  по-разному, и таблицей здесь ничего не сделать.

### Чем это опасно

**Ошибка в таблице не падает — она молча снижает оценку.** C# разобрался,
выдал осмысленные метки, получил 0.788 и ни на что не пожаловался. Go до
правки `:=` так же выдавал правдоподобные 0.851. Ни код возврата, ни число
пропущенных файлов такого не показывают.

Отсюда единственный надёжный способ проверки: **взять один алгоритм на двух
языках и потребовать совпадения последовательностей меток.** Так найдено
каждое расхождение из таблицы выше — ни одно не обнаружилось иначе.

Поэтому проверка живёт в тестах, а не в чьей-то памяти:
`tests/test_convergence.py` держит этот алгоритм на девяти языках и требует
совпадения с эталоном. **Добавляя язык, добавьте его туда же.** Пока язык так
не проверен, его числа означают меньше, чем кажется.

## Чего шаг 2 не умеет

- **`elif` и `else:` с вложенным `if` неразличимы.** В дереве это одна и та
  же форма — `If` внутри else-ветки. Считаем такую ветку `ELIF`: он
  встречается несравнимо чаще;
- **тройной оператор упрощён до `IF … END`** без ветки `ELSE`;
- **одно и то же действие на разных языках может дать разные метки**, если
  языки делают его по-разному. `items.length` в Java — это `DotAccess`, а
  `len(items)` в Python — `CALL`, и выровнять их нечем. Для таких пар шкала
  `COMBINED` не вполне общая;
- **неизвестный оператор** даёт имя, как его назвал Semgrep, а в составном
  присваивании — `OP=`. Второе важно: если бы знаком по умолчанию было `=`, с
  дописанным `=` вышло бы `==`, и неизвестный оператор замаскировался бы под
  сравнение. По той же причине `Eq` в позиции присваивания означает **обычное
  присваивание**, а не равенство: так Semgrep подаёт `:=` в Go, и без этого
  `total := 0` давало бы `ID == N0`;
- **ввод и вывод не убираются** — остаются вызовами и присваиваниями, и между
  языками с разным способом читать данные добавляют шум.

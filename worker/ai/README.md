# Воркер AI

Движок метода `ai` по контракту [`integritylens.ai/1`](../../docs/contracts.md#контракты-воркеров):
получает задание, оценивает каждый файл отдельно и пишет `result.json` или ошибку файла.
Под моделью — [aicode](../../tools/aicode/README.md) (GigaCheck, int2, CPU); воркер — общий
из [`worker/`](../README.md), отдельный процесс `python -m worker.ai run --input … --output …`
(как core у методов сравнения).

## Быстрый старт

Стек с настоящим движком и запрос — как в корневом README, с образцовым архивом:

```sh
docker compose -f infra/docker-compose.yml up --build -d
curl -F archive=@docs/samples/works.zip -F language=java -F title=lab3 http://localhost:8080/api/batches
docker compose -f infra/docker-compose.yml logs --tail 20 worker-ai
```

На каждую работу ставится свой прогон `ai`, воркер берёт их по одному. Замер на машине разработки
(Docker Desktop, 20 vCPU, 6 работ по 1.2–1.6 КБ): `HTTP 202` за 0.4 с, методы сравнения готовы
через секунду, все шесть AI-прогонов — за 9 мин 32 с (87–103 с на прогон). Журнал воркера:

```

worker-ai-1  | {"timestamp": "2026-11-23 15:57:04,778", "level": "INFO", "message": "Run completed", "batchId": "63850bcb-3206-4632-afcb-8c10dffbc333", "runId": "15e3d1cf-bdff-4e48-be8b-84140c3c56fb", "timings": {"downloadMs": 26.4, "coreMs": 101184.8, "validateMs": 7.4, "uploadMs": 10.8, "commitMs": 9.5}}
```

Оценки шести работ — 0.4538, 0.5323, 0.4676, 0.5118, 0.4910, 0.4543; тот же архив тремя днями раньше

```json
            "suspicious": [{"startIndex": 659, "endIndex": 1409, "confidence": 0.17752550542354584}]}]}
```

## Задание и результат

Задание — `{contract, runId, methodVersion, params, inputFiles[{submissionId, path}]}`, путь
относительно рабочего каталога. Результат — ровно один `{submissionId, status, score, suspicious,
reason?}` на входной файл: ошибки отдельных файлов не валят прогон, `done` их допускает.

## Как считаются оценки

| Контракт | Откуда берётся |
| --- | --- |
| `score` всей работы | доля помеченных байтов: сумма слитых фрагментов / размер файла |
| `suspicious[].startIndex/endIndex` | байтовые смещения UTF-8 с 0, правая граница исключена; aicode отдаёт символьные — конвертация с учётом BOM (+3 байта) и переводов строк |
| `suspicious[].confidence` | уверенность интервальной головки; у слитых пересекающихся фрагментов — максимум |
| `reason.code` | `NOT_PARSED` — не читается или не UTF-8, `TOOL_ERROR` — сбой инференса |

Переводы строк приводятся к `\n` до модели (`\r\n` и `\r`), как это делает текстовый режим, которым
читает файл сам aicode. Модель знает только `\n`: с `\r` её уверенность падает, и слабый сигнал не
проходит порог. Замер на одной учебной работе: с LF — 0.4676, с CRLF — 0.0000, фрагментов выше
порога нет. Смещения при этом остаются в байтах исходного файла.

Порог — параметр прогона `params.threshold`, по умолчанию `0.05`. Умолчание инструментной
карточки (0.8) на int2-кванте не пересекается ни одним confidence на реальном коде (максимум
~0.53), то есть даёт пустые `suspicious`; 0.05 даёт сигнал, но шумный — подробности и замеры
в [tools/aicode/README.md](../../tools/aicode/README.md). Модель фильтрует интервалы строго
`> threshold` — порог 0 отсекает и нулевые уверенности.

`methodVersion` вида `aicode-0.1.0+gigacheck-9fabe1503f+int2` собирается из версии пакета aicode
и метаданных артефакта (`aicode_model.json`), попадает в задание и результат и сверяется движком:
образ с одной версией модели не обработает задание под другую (ошибка без повторов). Вместе с
результатом в `runs` сохраняются `method_version` и фактически применённые `params`.

Детерминизм (одинаковые файлы, версия и параметры — одинаковые оценки): число потоков torch
зафиксировано в образе (`AICODE_THREADS`, по умолчанию 4) и не зависит от числа ядер машины.
На машине разработки один файл дал побитно одинаковые span'ы при 1, 4 и 8 потоках и при повторах,
а два независимых запуска на одном задании из трёх файлов — побитно одинаковый `result.json`.
Selfcheck в образе прогоняет файл дважды в одном процессе.

## Ресурсы и время

Замеры на машине разработки (Docker Desktop, 20 vCPU, лимит 4 ГБ):

| | 1 поток | 4 потока (умолчание) | 8 потоков |
| --- | --- | --- | --- |
| загрузка модели | 15 с | 15 с | 15 с |
| чанк до ~400 токенов (файл 1.4 КБ) | ~300 с | ~81 с | ~59 с |
| файл 7.5 КБ (3 чанка по 900 токенов) | — | 480 с | 342 с |

Модель грузится в каждом прогоне, но стоит это секунды: одна сдача ~1.5 КБ — около 1.7 мин,
30 таких работ — около 50 мин (воркер один, прогоны идут подряд). Время растёт с длиной чанка,
а не только с их числом. Память — 4 ГБ (пик ~2.6). Прогон AI — один на сдачу
(`runs.submission_id`, уникальный индекс); повторный анализ той же сдачи другой версией модели
потребует доработки схемы (в целевой модели ключ — `(submission_id, method_version)`).

Таймаут прогона `AICODE_TIMEOUT_SECONDS` (1800 с) при 4 потоках вмещает примерно 10 полных
чанков: более длинный файл завершается ошибкой `Core timeout` без повторов. Ускорить —
`AICODE_THREADS`, увеличить окно — `AICODE_TIMEOUT_SECONDS`.

Рабочие файлы и отчёты удаляются после прогона (временный каталог воркера); в MinIO уходит
только `result.json`, в БД — результат, версия и параметры.

## Образ и модель

`worker/ai.Dockerfile`, цель `ai`: зависимости aicode (заморожены в `uv.lock`) + модель из
[релиза репозитория](https://github.com/ITMO-Red-Team/IntegrityLens/releases/tag/aicode-model-v0.1.0)
(sha256 проверяется при скачивании). Сборка завершается selfcheck: мок проверяет контракт,
`real` — что модель грузится и результат воспроизводится (нужно ~4 ГБ памяти на время сборки).
Смена версии модели — build-args `AICODE_MODEL_URL` и `AICODE_MODEL_SHA256` (или переменные
того же имени в окружении compose).

Движок мокается отдельно от методов сравнения: `AICODE_ENGINE=mock` (у воркеров сравнения —
`CORE_ENGINE`), сценарии те же (`success`, `partial`, `fail_once`, `tool_error`, `invalid_input`).
Проверка без модели:

```sh
python -m worker.ai.selfcheck mock
python -m unittest discover -s worker/ai/tests -v
```

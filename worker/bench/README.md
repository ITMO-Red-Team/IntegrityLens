# Производительность воркеров

Замеры, асимптотика, что оптимизировано и что нет. Все числа получены командами из конца
этого файла и лежат в [`results/`](results/).

**Условия.** Apple M4 Max, Docker `linux/arm64`, контейнер `--cpus 2 -m 4g`: это похоже на
небольшую виртуалку по числу ядер, но не по скорости ядра. На настоящей x86-виртуалке не мерили:
абсолютные числа там наверняка больше, соотношения должны остаться. Вход, если не сказано иное, — 50 различных
решений ConPlag как они сданы: 3.8 КиБ и 380 меток на файл в среднем, 1225 пар. ConPlag в
репозиторий не входит, `research/one` скачивает его сам. Все разделы, кроме
[шаблонных алгоритмов](#шаблонные-алгоритмы), измерены без их стирания: это замеры самих методов.

## Итог

| 50 работ, 2 ядра | Было | Стало | |
|---|---|---|---|
| structsim, core целиком | 61.5 с | **2.01 с** | ×30 |
| JPlag, core целиком | 1.63 с | **0.68 с** | ×2.4 |
| от загрузки до начала работы воркера | 1 561 мс, до 2 090 мс | **87 мс** | ×18 |
| проверка результата | 132 мс | **21 мс** | ×6 |
| зависание JPlag на запросе к GitHub | без таймаута | запроса нет | |

«Было» у structsim — шаги из `tools/structsim` как есть, на Python, но уже без контейнера на
файл. «Было» у JPlag — CLI с ключами по умолчанию. Оценки при этом не изменились: у structsim
это проверено побитовым сравнением с эталоном, у JPlag изменились только ключи JVM, а не сам
инструмент. Задержка подхвата растёт с числом файлов: `createdAt` ставится в начале транзакции
загрузки, а воркер узнаёт о задании при её фиксации.

Работа воркера в живом стеке, от захвата задания до записи результата в БД: **0.87 с** у JPlag
и **2.13 с** у structsim ([`e2e.csv`](results/e2e.csv)), со стиранием шаблонов по умолчанию **0.92 с**
и **2.09 с**. Настоящий JPlag теперь вдвое быстрее прежнего мока: мок на этом входе занимал 1.75 с,
почти всё — поиск фрагментов на Python.

## Асимптотика

`n` — работ в наборе, `T` — меток в работе (≈3.3 на строку), `P = n(n−1)/2` — пар, `F` —
совпавших кусков. Показатель степени — наклон на удвоении, по `results/`.

| Этап | Было | Стало | Измерено |
|---|---|---|---|
| подхват задания | опрос, до 2 с | уведомление | 87 мс, из них почти всё — транзакция API |
| скачивание | `O(n)` | `O(n)` | 50 мс |
| шаг 1 | `n·(c + αT)` | то же, поделено на ядра | `n^1.0`, `c ≈ 58 мс`; `T^1.0` |
| шаг 2 | `O(nT)` | `O(nT)` | `T^1.0` |
| шаг 3, мера по порядку | `P·T²` | `P·T^1.5` | `n^2.0` |
| шаг 3, мера по функциям | `P·B²·…`, дважды | один раз, с отсечением по границе | |
| тайлы | `P·T^2.7`, кубически в худшем | `P·T^1.9`, квадратично в худшем | `n^2.0` |
| шаг 4 | `n³` | `n³` | 21 мс при `n = 50` |
| проверка результата | `n·P + F` | `P + F` | 21 мс |
| JPlag | `c + nT + P·T^1.8` | то же, меньше `c` | см. ниже |

Подробно про шаг 3 и тайлы — в [`docs/native.md`](../../tools/structsim/docs/native.md).

**От числа работ.** До `n = 50` квадрат почти не виден ни у кого: у structsim сравнение занимает
0.07 с из 2 с и растёт как `n²`, но разбор, линейный по `n`, больше в 25 раз
([`*_by_count.csv`](results/)):

| Работ | Пар | structsim | из них шаг 3 | JPlag |
|---|---|---|---|---|
| 5 | 10 | 0.25 с | 2 мс | 0.24 с |
| 10 | 45 | 0.40 с | 3 мс | 0.28 с |
| 20 | 190 | 0.79 с | 13 мс | 0.37 с |
| 30 | 435 | 1.20 с | 28 мс | 0.48 с |
| 40 | 780 | 1.63 с | 53 мс | 0.57 с |
| 50 | 1225 | 2.03 с | 74 мс | 0.68 с |

Замечание с защиты про квадратичную сложность верно: число пар квадратично, и контракт требует
оценку каждой. Предел `n ≤ 50` делает это несущественным. Если предел когда-нибудь снимут, при
той же цене пары 1 000 работ займут ~30 с шага 3 на двух ядрах, а дальше понадобится предварительный
отбор кандидатов, он изменит контракт.

**От длины программы.** 10 работ, 2 ядра, синтетика ([`*_by_size.csv`](results/)):

| Строк в файле | Меток | structsim | из них шаг 3 | JPlag |
|---|---|---|---|---|
| 100 | 324 | 0.41 с | 3 мс | 0.29 с |
| 400 | 1 343 | 0.58 с | 9 мс | 0.32 с |
| 1 600 | 5 517 | 1.24 с | 54 мс | 0.55 с |
| 6 400 | 21 627 | 4.29 с | 568 мс | 5.28 с |
| 25 600 (~1 МиБ) | 87 927 | 21.8 с | 7.7 с | — |

Здесь structsim почти линеен, а JPlag квадратичен (`T^1.8`): с нескольких тысяч строк он
становится медленнее structsim. У него своё сравнение, и мы его не меняем.

**Предел входа.** API пропускает до 50 файлов по 1 МиБ. Таких входов мы целиком не гоняли,
это прикидка по таблице выше: structsim на двух ядрах около 5 минут, 800 МБ памяти на разбор
двух файлов разом плюс около 1 ГБ на программы. JPlag на двух ядрах около получаса, то есть
не уложится в `CORE_TIMEOUT_SECONDS` = 600 и завершится ошибкой после трёх попыток. Измеренная
точка: 50 файлов по 6 400 строк (11.6 МБ) у JPlag — 98 с. Для учебных работ это далеко за
пределами обычного: в наборах `research/one` самый большой файл — 190 КиБ, 99% меньше 14 КиБ.

## Что сделано

| Что | Эффект | Цена |
|---|---|---|
| [шаг 3 и тайлы на Rust](../../tools/structsim/docs/native.md) | 58 с → 0.07 с | второй язык; числа сверяются тестом с эталоном |
| индекс кусков в поиске совпадений | внутри Rust: 3 программы по 32 000 меток, 1 208 → 63 мс | 60 строк |
| разбор параллельно по лимиту контейнера | 3.5 → 1.9 с на двух ядрах | |
| копии файлов разбираются один раз | минус 63 мс на копию | |
| короткий путь в `semgrep-core` | выгрузка в 1.4 раза меньше: путь есть в каждом токене | |
| без сборщика мусора в процессе core | `json.loads` большой выгрузки: 197 → 94 мс | процесс короткий, циклов нет |
| JPlag без проверки версии на GitHub | минус 0.46 с и никакого зависания | прокси в никуда: другого способа в CLI нет |
| JVM: SerialGC, AOT-кэш, только C1 на малых входах | 1.16 → 0.68 с, CPU вдвое меньше | сборка образа на пару секунд дольше |
| `fastjsonschema` вместо `jsonschema` | проверка 132 → 21 мс, импорт 42 → 5 мс | строгость та же на 15 сломанных документах |
| проверка результата один раз, без `n³` | минус ещё один проход | |
| `LISTEN/NOTIFY` вместо опроса | 1 561 → 87 мс; в простое нет соединений раз в 2 с | триггер в БД, опрос раз в 15 с как страховка |
| ожидание core без `sleep(0.2)` | минус до 200 мс на прогон | |
| свои минимальные JVM и `semgrep-core` | загрузка 72 МБ вместо образа на 1.6 ГБ, JVM 88 МБ вместо JDK на 600 МБ | образы по 620–640 МБ вместо 650 МБ + 1.6 ГБ |

Заодно, не про скорость, но без этого настоящие методы работали бы плохо:

- core убивается вместе с детьми: раньше детей не было, а kill только процесса core оставлял бы
  работать JVM. Убитых потомков забирает `init: true`;
- `CORE_THREADS` по умолчанию смотрит на лимит контейнера: `os.cpu_count()` его не видит и запустил
  бы 14 процессов на двух ядрах;
- JPlag падал на обычном коде с длинной кириллической строкой или таблицей в начале файла
  ([ловушка 6](../../tools/jplag/pitfalls.md)) и на метке порядка байтов. Лечится комментарием в
  первой строке копии файла. Оценки и фрагменты на 1225 парах те же, время то же;
- воркер, которого останавливают посреди задания, возвращает его в очередь и не тратит попытку.

**JPlag и C1.** Второй компилятор JVM на коротком запуске не окупается: на типичном наборе он тратит
ядра и ничего не успевает дать. На длинном запуске наоборот, поэтому режим выбирается по размеру:

| Вход, 50 файлов | Оба компилятора | Только C1 |
|---|---|---|
| 0.2 МБ | 1.19 с | **0.89 с** |
| 0.7 МБ | 2.00 с | **1.55 с** |
| 2.9 МБ | **6.34 с** | 7.16 с |

Порог — 1 МиБ исходников. В этой таблице ещё старая проверка результата, разница от неё не зависит.

## Шаблонные алгоритмы

Функции, похожие на функции из набора [`core/templates/`](../core/templates/), стираются из копии
исходника до запуска метода ([контракт](../core/CONTRACT.md#шаблонные-алгоритмы)). В наборе 9 файлов и
214 функций: ввод, сортировки, поиск, числа, графы, структуры данных, динамика, строки, мелкие
помощники для массивов. Основа написана по учебникам, добавки сделаны по тому, что авторы ConPlag
вычистили вручную из решений обучающей части.

**Качество.** ROC-AUC на размеченных наборах, в скобках 95% интервал прироста, парный бутстрэп
([`templates_quality.csv`](results/templates_quality.csv)). Пороги и добавки подбирались по train и
IR-Plag, поэтому итог читается по test ConPlag; «новые» — пары test, решений которых нет в train.

| Набор, пары | Оценка | Как есть | Со стиранием | Прирост |
|---|---|---|---|---|
| ConPlag как сдано, test | JPlag `max` | 0.906 | **0.927** | +0.020 [+0.008; +0.033] |
| | JPlag `avg` | 0.860 | **0.907** | +0.047 [+0.029; +0.067] |
| | structsim | 0.852 | **0.895** | +0.043 [+0.026; +0.064] |
| ConPlag как сдано, новые | JPlag `max` | 0.912 | **0.934** | +0.022 [+0.009; +0.035] |
| | JPlag `avg` | 0.887 | **0.923** | +0.037 [+0.017; +0.057] |
| | structsim | 0.889 | **0.927** | +0.038 [+0.018; +0.062] |
| ConPlag вычищенный, test | JPlag `max` | 0.933 | 0.935 | не значим [−0.003; +0.005] |
| | JPlag `avg` | 0.932 | 0.935 | не значим [−0.001; +0.006] |
| | structsim | 0.962 | 0.963 | не значим [−0.001; +0.004] |
| IR-Plag, короткие учебные | JPlag `max` | 0.544 | 0.544 | не значим |
| | JPlag `avg` | 0.556 | 0.557 | не значим |
| | structsim | 0.611 | 0.618 | +0.007 [+0.003; +0.013] |

Стирается 26% строк работ как они сданы, 3.4% вычищенных и 0.9% коротких учебных. Что остаётся
стёртым на вычищенном ConPlag, это в основном забытые авторами шаблоны: конструкторы `Pair`, чтение
массива, сортировка с перемешиванием. Ни одна работа из-за стирания не выпала. До ручной чистки всё
же далеко (structsim 0.895 против 0.962): у участников соревнований много личных библиотек, общим
набором их не покрыть.

**Почему функции целиком, а не `-bc` или куски.** Подбирали на train, сверяя стёртое с тем, что
вычистили авторы. Точность — какая доля стёртых строк вычищена и вручную, полнота — какая доля
вычищенного стёрта:

| Правило | Точность | Полнота | Стёрто на вычищенном | AUC на вычищенном, JPlag `max` |
|---|---|---|---|---|
| `-bc` JPlag, итоговый набор | | | 14% меток | 0.910 вместо 0.939 |
| куски меток structsim от 20 меток, первая версия набора | 93% | 28% | 1.7% меток | |
| целые функции, первая версия набора | 95% | 46% | 2.8% строк | |
| **целые функции, итоговые набор и пороги** | 95% | 65% | 3.4% строк | 0.939 |

`-bc` задаёт порог сравнения общим с основным `-t`, и на большом наборе девять токенов находятся
почти везде ([ловушка 8](../../tools/jplag/pitfalls.md)). Куски меток дают мало, потому что функцию
редко пишут метка в метку, а короткие куски уже совпадают случайно. Целые функции к тому же работают
одинаково для обоих методов, а `main` при этом остаётся: это сама программа, а не вставленный алгоритм.

**Как сравниваются функции.** Форма функции — токены, в которых имена, числа, типы и оформление
заменены на общие: `long gcd(long a, long b)` и `int f(int x, int y)` совпадают. Похожесть —
`SequenceMatcher.ratio` по форме.

**Порог.** Плоский порог не годится. У коротких функций сходство растёт быстро: обычная сумма с условием
в цикле уже на 0.78 похожа на функцию из набора, хотя логика в ней своя. Отсюда два порога.

| Порог | Стёрто: как сдано / вычищено / учебные | AUC на train, JPlag `max` как сдано | Выпало работ IR-Plag |
|---|---|---|---|
| 0.6 везде | 35% / 8.2% / 13% | 0.952 | 16 |
| 0.7 везде | 31% / 4.8% / 7.2% | 0.958 | 6 |
| 0.8 везде | 26% / 3.1% / 3.1% | 0.949 | 1 |
| 0.9 везде | 21% / 1.8% / 0.5% | 0.944 | 0 |
| **0.85 короче 60 токенов, иначе 0.7** | 26% / 3.4% / 0.9% | 0.945 | 0 |

При плоском пороге 0.6 стираются уже настоящие `solve`: у JPlag AUC на test падает с 0.927 до 0.914 на
сданных работах и с 0.935 до 0.927 на вычищенных. У выбранного правила запас от этого обрыва есть. Плата —
около сотой AUC на train по сравнению с плоскими 0.7, зато в простых учебных заданиях своя логика не пропадает.

**Цена.** 50 работ, 2 ядра ([`templates_speed.csv`](results/templates_speed.csv)):

| | Без стирания | Со стиранием | Само стирание |
|---|---|---|---|
| JPlag | 0.69 с | 0.73 с | 63 мс |
| structsim | 1.96 с | **1.85 с** | 64 мс, зато разбор на 143 мс быстрее |

Асимптотика линейна по длине кода: токены и поиск методов за `O(L)`, на функцию — отбор кандидатов по
кускам формы. 2.3 МБ разбираются за 0.21 с. На полном сравнении с `difflib` ушло бы вдвое больше, поэтому
сначала идёт отсечка по наибольшей общей подпоследовательности: `ratio` не больше неё, а битовый алгоритм
считает её на порядок быстрее. Решения те же: 0 расхождений на 2 937 различных формах функций ConPlag.
Файлы, в которых скобки не сходятся, и файлы, собранные нарочно медленными, разбор не ломают: их прогоняет тест.

**Что это не решает.** Правило смотрит только на функции. Алгоритм, вписанный прямо в `main`, не
сотрётся. Если задание само в том, чтобы написать Дейкстру, у всех работ останется только обвязка: для
такого есть `ignoreTemplates: false`, в API его пока не задать. Переставленный или сильно переписанный
шаблон останется в сравнении, и наоборот: чужая функция, почти совпавшая с шаблоном, из сравнения выпадет.

## Что не сделано

| Идея | Почему нет |
|---|---|
| ускорить старт `semgrep-core` | 58 из 63 мс уходят до открытия файла: инициализация бинарника на 262 МБ и запуск `uname` из него. Настроек на это нет. `OCAMLRUNPARAM` даёт 2–3%. Можно было бы форкать уже запущенный процесс через `LD_PRELOAD`, потенциал ×6 на этом этапе, но это хрупкий хак поверх чужого бинарника. При 2 секундах на набор он того не стоит |
| шаг 2 на Rust | 1.7 мс на файл против 62 мс `semgrep-core`, а на 12 800 строках 0.2 с против 1.1 с. Не окупается ни на какой длине, зато появилась бы вторая реализация сложной таблицы узлов |
| постоянная JVM | по оценке минус ~0.4 с на прогон, но 400 МБ памяти постоянно и общий процесс на чужие исходники |
| Java API вместо CLI JPlag | по оценке минус 0.1–0.2 с на записи отчёта, но привязка к внутренним классам. Отчёт ещё и полезен: его открывает просмотрщик JPlag |
| параллельное скачивание и загрузка | попробовано и убрано: 30 мс последовательно против 32 мс в 8 потоков, MinIO рядом |
| `contrast-z` за `n²` | 21 мс при `n = 50`. `fmean` и `pstdev` здесь точные, замена на суммы изменила бы последний бит |
| предварительный отбор пар | контракт требует все пары, а при `n ≤ 50` выигрывать нечего |
| кеш разбора по хешу исходника | помог бы только при повторной загрузке почти тех же работ, а это редкость |

| Эксперимент | Образ | Что меняет | Время |
|---|---|---|---|
| `worker.bench.templates` | оба | правило стирания, качество на разметке | 5 мин на образ |
| `templates` | оба | цена стирания, настоящие решения и длинные файлы | 1 мин |
| `before_after` | оба | настройки: Python или Rust, ключи JVM | structsim ~6 мин, JPlag 1 мин |
| `by_count` | оба | число работ, настоящие решения | 1 мин |
| `single` | оба | запускать с разным `--cpus` | 1 мин |
| `by_size --count 10` | оба | длина, синтетика | 3–5 мин |
| `worker.bench.pair_cost` | structsim | цена пары: эталон и native | 4 мин |
| `worker.bench.e2e` | снаружи, нужен стек | весь путь через API | 1 мин |

Значения по медиане повторов. Синтетический генератор — [`corpus.py`](corpus.py): воспроизводится
по зерну, каждая четвёртая программа списана с предыдущей. Он собран из типовых функций, которые
были бы стёрты, поэтому все эксперименты, кроме `templates`, идут с `ignoreTemplates: false`.
